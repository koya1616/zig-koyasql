# ADR 0001: ストレージエンジンに B+木を採用し、書き込み最適化を設計対象に含める

- Status: Accepted
- Date: 2026-11-12

## Context

自作 RDBMS のストレージエンジン / インデックス構造を決める必要がある。

- 読み込み（点検索・範囲検索・`ORDER BY`）と書き込みの**両方**を重視する
- 学習目的のため、実装の段階性と理解しやすさも判断材料になる
- 関連: [設計・実装チェックリスト](../design-checklist.md) 1.1 / 5.1

## Decision

### 1. B+木を採用する

インデックス構造の基盤として **B+木を採用する**。

- 内部ノードはキーと子ページへのポインタのみ、リーフノードはキーと値を持ち、リーフ間をリンクする
- 点検索 O(log N) と範囲走査（リーフリンクによるシーケンシャル I/O）を同一構造で扱える
- リーフに列値を含めればカバリングインデックス（インデックスオンリースキャン）に発展できる

### 2. 書き込みも重視し、memtable + バックグラウンド Compaction を書き込み経路とする

B+木は書き込み（ページ分割・親更新・ランダム I/O）が弱点になりやすい。そこで**書き込み直後のデータだけを一時的なメモリ上の memtable（または追記型バッファ）で受け止め、バックグラウンドでマージ（Compaction）しながら最終的な B+木セグメントへ反映する**アーキテクチャを採用する。

```
INSERT/UPDATE
   │
   ▼
WAL (先行して永続化)
   │
   ▼
memtable (追記型・メモリ)
   │  threshold 超過
   ▼
immutable memtable ──background──▶ Compaction ──▶ B+木セグメント (不変)
                                                      │
読み取り: memtable → immutable → B+木セグメント（新しい順にマージ参照）
```

この構成により、B+木のページを**その場で書き換えるのではなく、不変セグメントとして構築**できる。結果としてページ分割・マージの並行性制御を大幅に単純化できる。

この書き込み経路の中で、以下を**設計対象として明記**する。

- **メモリ層でのバッファリング / 遅延書き込み**
  - 書き込みを即座にページへ反映せず、メモリ上でまとめてから書き戻す（= memtable と Compaction の interval 設計）
- **書き込み順序の工夫と初期化**
  - ランダム書き込みをシーケンシャルに近づける（キー順 / ページ順 / セグメント順の書き出し）
  - ページ・セグメントの事前初期化（フォーマット）と再利用
- **デデュプリケーション（重複排除）**
  - 同一キー・同一プレフィックスの重複エントリを排除する（例: PostgreSQL 13 以降の btree deduplication 相当）
- **圧縮**
  - ページ / セグメント単位の圧縮、プレフィックス圧縮、可変長キーの格納効率
- **同時実行制御（Concurrency Control）の最適化**
  - ラッチ / ロック粒度、分割時の並行性、読み手をブロックしない方式

### 3. memtable のデータ構造にスキップリストを採用する

書き込みを受け止める memtable は**スキップリスト**で実装する。

- 挿入・検索・削除が平均 O(log N) で、**バランス回転が不要**
- キー順のイテレーションができ、immutable memtable を**キー順のまま B+木セグメントへフラッシュ**できる
- ポインタ更新が局所的で、並行書き込み（細粒度ロック / ロックフリー）へ拡張しやすい
- 実装が比較的コンパクトで、Zig でも扱いやすい

設計上の決定事項:

- 最大レベルと昇格確率 p（例: p = 0.25 / 0.5、最大レベル 32）
- レベル生成の乱数はシード可能にし、テストを決定論的にする
- 並行性モデルはまず**単一ライター + 複数リーダー**とし、必要なら細粒度ロックへ発展させる
- 削除は tombstone の挿入で表現し、セグメントへ反映されるまで保持する

他の候補を採用しない理由:

- **赤黒木 / AVL 木**: 回転を伴うため、並行更新時のポインタ更新範囲が広がる
- **ソート済み配列**: 挿入が O(N) になり、書き込み重視の方針に反する
- **ハッシュテーブル**: 順序走査ができず、フラッシュ時に別途ソートが必要になる
- **メモリ上の B+木**: ページ管理が過剰で、memtable には重い

### 4. Compaction 後のセグメントは B+木で構築する

Compaction が最終的に書き出すセグメントは、**不変の B+木**とする。ソート済み SSTable ではなく、内部ノード + リーフリンクを持つ B+木として構築する。

- セグメント内の点検索は内部ノードを辿る O(log N) で済み、全キーのインデックスを別途メモリに持たなくてよい
- リーフリンクにより、セグメント内の範囲走査をシーケンシャルに実行できる
- 入力が memtable / 既存セグメントの**ソート済み列**なので、**ボトムアップの一括構築（bulk load）**で作れる。In-place のページ分割は発生しない
- セグメントは不変なので、構築後の分割・マージに伴う並行性制御が不要

設計上の決定事項:

- セグメントは構築時に fill factor を決めてほぼ満杯まで詰める（読み取り専用のため）
- セグメントのフッタに最小キー / 最大キー / エントリ数 / チェックサム / 圧縮情報を持たせ、読み取り時に木を辿る前の足切りに使う
- Compaction は「複数セグメントのマージソート + 新しい B+木の bulk load」として実装する

ソート済み SSTable を採用しない理由:

- SSTable は範囲走査のたびにブロック索引を別途引く必要があり、B+木の内部ノードと役割が重複する
- セグメントごとにキー範囲とリーフリンクを持てるため、複数セグメントのマージ読み取りでも順序を保ちやすい
- ただし実装の単純さでは SSTable が優るため、構築コストが問題になった場合は見直す

## Rationale

- B+木単体では書き込み増幅と分割時の並行性が課題になる。memtable と不変セグメント化でその弱点を緩和できる
- 書き込みを追記型バッファで受けるため、WAL との親和性が高い
- セグメントが不変になることで、デデュプリケーション・圧縮・チェックサムをセグメント単位で適用しやすい
- 読み取り側は B+木の順序性を保てるため、範囲走査と `ORDER BY` の利点を維持できる

## Consequences

### 良い面

- 書き込みのホットパスが追記 + メモリ操作になり、ランダム I/O を削減できる
- 分割・マージをバックグラウンドに追い出せる
- セグメント単位で圧縮・重複排除・統計収集ができる

### 悪い面 / 注意点

- この構成は実質的に **LSM の書き込み経路 + B+木の読み取り構造**というハイブリッドになる。純粋な in-place B+木とは設計が異なる点を意識する
- 読み取りは memtable → immutable → 複数セグメントのマージ参照になり、**read amplification** が発生する
- memtable のクラッシュ耐性のために WAL が必須
- Compaction のスケジューリング、write stall（書き込み停止）対策が必要
- セグメントの GC / 古いバージョンの回収（MVCC と連動）が必要
- セグメントを B+木にすると、SSTable より構築処理（内部ノード生成・リーフリンク）が増える
- セグメント数が増えると、読み取り時に複数の B+木を辿る分だけ read amplification が増える
- スキップリストはノードごとに多段ポインタを持つため、配列などに比べてメモリオーバーヘッドがある
- スキップリストの性能は確率的で、最悪ケースの計算量保証はない
- 並行削除を行う場合、GC のない Zig ではノード回収（エポックベースなど）を別途設計する必要がある

## Open Questions

- Compaction の方式（leveled / tiered / size-tiered）と世代管理
- クラスタ化インデックス（InnoDB 型）か、ヒープ + 非クラスタ化 B+木（PostgreSQL 型）か
- MVCC のバージョンをセグメント内に持つか、Undo / 別領域に置くか

## Revisit Conditions

以下に該当したら本 ADR を見直す。

- 書き込みがほぼ逐次追記で、範囲検索が不要になった（LSM / 追記ログのみで足りる）
- 読み取りレイテンシが Compaction に支配されるようになった
- 単一ノード・組み込み用途に絞り、同時実行制御を大幅に簡略化できると判断した
