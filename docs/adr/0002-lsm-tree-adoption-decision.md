# ADR 0002: LSM ツリー（書込最適化）の採用判断

- Status: Accepted
- Date: 2026-11-14
- Related: [ADR 0001](0001-storage-engine-b-plus-tree.md) / [設計・実装チェックリスト](../design-checklist.md) 1.1

## Context

チェックリスト 1.1 の「LSM ツリー（書込最適化）を採用するか判断」に対して、判断基準と結論を残す必要がある。

ADR 0001 でストレージエンジンは「WAL → memtable → immutable memtable → Compaction → 不変 B+木セグメント」と決定済みであり、これは**書き込み経路が LSM 的、読み取り構造が B+木**のハイブリッドである。したがって本 ADR の論点は「純粋な LSM に置き換えるか」、より狭くは「Compaction 後のセグメントを SSTable にするか」である。

## Decision

1. **現時点では純粋な LSM ツリーをストレージエンジンとして採用しない。** ADR 0001 のハイブリッド構成（LSM 的な書き込み経路 + 不変 B+木セグメント）を維持する。
2. 将来 LSM を評価する場合は、既存エンジンへ混在させず、**Segment インターフェース（`get` / `scan` / `merge`）の裏に SSTable 実装を追加**して測定で比較する。
3. 判断は以下の基準で行う。

### 判断基準 1: ワークロード

| 指標 | LSM 寄り | B+木寄り |
| --- | --- | --- |
| 書き込み:読み込み | 10:1 以上 | 1:1 前後 |
| 更新・削除の比率 | 低い（追記中心） | 高い |
| 範囲検索・`ORDER BY`・前置一致 | 少ない | 多い（30% 以上など） |
| アクセス | 最新データ中心（時系列・ログ） | 任意キーの点検索 |
| データ量 | RAM に収まらない巨大データ | RAM に収まる〜中規模 |
| 書き込みバースト | 大量一括取り込み（COPY / ingest） | 定常的 |

### 判断基準 2: 3つの増幅率

LSM は「書き込み最適化」と呼ばれるが、**書き込み増幅が必ず下がるわけではない**。以下を必ず測る。

- **Write Amplification (WA)** = ストレージへ書いたバイト / 論理書き込みバイト
  - in-place B+木: ページ書き換えで比較的低い
  - LSM leveled: 10〜30 倍になり得る / tiered: 低いが read / space amplification が悪化
- **Read Amplification (RA)** = 1 回の読み取りで触るファイル / ページ数
  - B+木: 1 本の木を辿る / LSM: 複数 run のマージ参照
- **Space Amplification (SA)** = 実ストレージ / 論理データ量
  - LSM leveled ≒ 1.1 / tiered は最大 2 倍程度 / B+木は断片化次第

p99 レイテンシ SLO、SSD 寿命（WA）、ディスク容量（SA）のどれが制約かを先に決める。制約が WA なら LSM の利点は薄い。

### 判断基準 3: 機能要件

| 要件 | B+木 | LSM |
| --- | --- | --- |
| 一意性制約（UNIQUE / PK） | 自然に実装 | 挿入前読み取りが必要で競合処理が複雑 |
| セカンダリインデックス | インデックスごとに B+木 | インデックスごとに LSM、またはセグメント内索引が必要 |
| MVCC / スナップショット | Undo 等と連携 | キーにバージョンを持たせやすいが GC が難しい |
| 範囲ロック / ファントム防止 | リーフリンクと相性が良い | マージイテレータ越しのロックが難しい |
| バルクロード | bulk load で高速 | 本来得意 |

### 判断基準 4: 運用・障害時のコスト

- Compaction ストール / write stall の有無と許容度
- tombstone の GC と削除データの物理回収
- クラッシュリカバリ時間（WAL 再生 + セグメント状態）
- バックアップ / PITR のしやすさ
- 可観測性（run 数、level ごとのサイズ、compaction 遅延）を出せるか

### 判断基準 5: 実装・学習コスト

- Zig は GC なし・手動メモリ管理。**不変セグメントは並行性制御が圧倒的に楽**（ADR 0001 の利点）。
- 不変 B+木はソート済み入力からのボトムアップ bulk load で構築でき、in-place 分割の並行性問題を回避済み。
- LSM の SSTable は構築が単純な一方、**compaction スケジューラ・level 管理・マージイテレータ**の実装量が増える。
- 「LSM を学ぶ」ことが目的なら、既存エンジンに混ぜず**別ストレージエンジンとして実装**する方が比較できて学習効果が高い。

### 判断基準 6: スコアカード（迷った場合）

各項目 1〜5 点、重み付き合計。

| 基準 | 重み | B+木（不変セグメント） | LSM |
| --- | --- | --- | --- |
| 点検索性能 | 20% | 5 | 3 |
| 範囲検索 / `ORDER BY` | 20% | 5 | 4 |
| 書き込みスループット | 20% | 4 | 5 |
| WA / SSD 寿命 | 10% | 4 | 2 |
| SA / 容量効率 | 10% | 5 | 3 |
| 一意性・2 次索引 | 10% | 5 | 2 |
| 実装・運用の単純さ | 10% | 3 | 3 |
| **合計** | 100% | **4.5** | **3.4** |

書き込み比率を 40% 以上に上げ、範囲検索を 10% 未満に下げると LSM が逆転する。

## Rationale

- 対象ワークロードは読み込み・書き込みの**両方**を重視しており、LSM の書き込み特化が決定的な利点にならない
- 範囲検索・`ORDER BY`・セカンダリインデックス・一意性制約は B+木の方が自然に実装できる
- ADR 0001 の memtable + Compaction により、**LSM の書き込み利点の一部はすでに享受済み**である
- 不変セグメントは Zig の手動メモリ管理・並行性制御と相性が良い
- 純粋 LSM の導入は compaction 方式・level 管理・GC の設計を追加し、学習初期の実装段階性を損なう

## Consequences

### 良い面

- 読み取り側の順序性と点検索性能を維持できる
- 一意性制約・セカンダリインデックス・範囲ロックの設計を単純に保てる
- 実装の段階性を保ち、まず動くエンジンを作れる

### 悪い面 / 注意点

- 書き込みがほぼ追記-only のワークロードでは、LSM に比べて書き込み効率で劣る可能性がある
- セグメント数が増えた場合の read amplification は別途対策が必要
- LSM を採用しなかった判断は、ワークロード変化に応じて再評価が必要

## Open Questions

- Compaction 方式（leveled / tiered / size-tiered）と世代管理（ADR 0001 から継続）
- SSTable セグメントを比較実装する場合の評価用ワークロードと指標の定義

## Revisit Conditions

以下に該当したら本 ADR を見直す。

- 書き込みがほぼ逐次追記になり、範囲検索が不要になった
- 読み取りレイテンシが Compaction に支配されるようになった
- 組み込み・単一ノード用途に絞れて同時実行制御を大幅に簡略化できると判断した
- セグメントの bulk load コスト、またはセグメント数増加による read amplification が問題になった
