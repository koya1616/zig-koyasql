# ADR 0003: 単純なアペンドオンリー（ログ型）ストレージの採用判断

- Status: Accepted
- Date: 2026-11-14
- Related: [ADR 0001](0001-storage-engine-b-plus-tree.md) / [ADR 0002](0002-lsm-tree-adoption-decision.md) / [設計・実装チェックリスト](../design-checklist.md) 1.1

## Context

チェックリスト 1.1 の「単純なアペンドオンリー（ログ型）を採用するか判断」に対して、判断基準と結論を残す必要がある。

本 ADR で扱う「単純なアペンドオンリー（ログ型）」は、**レコードをファイル末尾へ順次追記し、その場で書き換えない**ストレージである。更新は新しいレコードの追記、削除は tombstone の追記で表現し、古いレコードの回収には別途 GC / Compaction を必要とする。Bitcask のように「追記ログ + インメモリハッシュ索引」で点検索を成立させる構成を含む。

以下とは区別する。

- **WAL**: 耐久性のための追記ログであり、主データの格納先ではない。ADR 0001 の書き込み経路にはすでに含まれる
- **LSM ツリー**: 複数のソート済み run をマージする構造。単純な追記ログとは異なり、キー順のマージを前提とする

## Decision

1. **プライマリなストレージエンジンとしては採用しない。** ADR 0001 の「memtable + Compaction + 不変 B+木セグメント」を維持する。
2. ただし、以下の用途ではアペンドオンリー構造を採用する。
   - **WAL**（ADR 0001 の書き込み経路に含まれる）
   - **監査ログ / 変更履歴 / 時系列イベント**など、追記専用が自然なデータ
   - **初期プロトタイプの最小永続化**（本番の読み取り経路ではなく、クラッシュリカバリの学習用）
3. 「追記ログ + インメモリハッシュ索引」（Bitcask 型）は、**全キーが RAM に収まる点検索用途**に限って候補とする。RDBMS の主ストレージにはしない。

## 判断基準

### 1. ワークロード

| 指標 | アペンドオンリー寄り | B+木寄り |
| --- | --- | --- |
| 更新・削除 | ほぼなし | 多い |
| アクセス | 追記と最新値の点検索 | 任意キーの点検索・範囲検索 |
| 順序 | 到着順・時系列 | キー順 |
| 範囲検索 / `ORDER BY` | 不要 | 必要 |
| キー数 | RAM に収まる（ハッシュ索引） | RAM に収まらない |
| データ量 | 追記中心で単調増加 | 更新してもサイズが安定 |

### 2. 読み取り特性

- **点検索**: ハッシュ索引があれば O(1)。索引がなければ末尾から走査するため O(N)
- **範囲検索**: キー順で並んでいないため、全走査 + ソートか別索引が必要
- **`ORDER BY` / JOIN / 集約**: 専用の順序索引なしでは非効率
- **MVCC / スナップショット**: バージョンを追記で表現できるが、可視性判定と GC が別途必要

### 3. 空間と回収

- 更新・削除が古いレコードを残すため、**space amplification が増大する**
- Compaction / GC がないとファイルが無制限に成長する
- 回収には有効レコードの書き直しが必要で、結局は「追記 + マージ」になる
- WAL として使う場合も、checkpoint に伴う切り詰めが必要

### 4. 耐久性・リカバリ

- 追記 + fsync は単純で、クラッシュ時の整合性を理解しやすい
- 起動時に全ログを再生するとデータ量に比例して遅くなる。**checkpoint / snapshot が必要**
- 部分書き込みや破損レコードの検出（長さ・チェックサム）が必要

### 5. 実装・学習コスト

- 最小の永続化としては最も単純で、Zig でも実装しやすい
- ただし RDBMS の要件（範囲検索、2 次索引、更新、トランザクション）を満たすには索引と GC を足していくことになり、**最終的に B+木 / LSM に近づく**
- 初期マイルストーンとしては有用だが、最終形にはならない

### 6. スコアカード

各項目 1〜5 点、重み付き合計。RDBMS の主ストレージとして評価する。

| 基準 | 重み | B+木（不変セグメント） | アペンドオンリー |
| --- | --- | --- | --- |
| 点検索性能 | 20% | 5 | 3 |
| 範囲検索 / `ORDER BY` | 20% | 5 | 1 |
| 書き込みスループット | 20% | 4 | 5 |
| 更新・削除 | 10% | 5 | 2 |
| SA / 容量効率 | 10% | 5 | 2 |
| 一意性・2 次索引 | 10% | 5 | 2 |
| 実装・運用の単純さ | 10% | 3 | 5 |
| **合計** | 100% | **4.6** | **2.9** |

### 7. 判定ルール

- 更新・削除がなく、範囲検索も不要で、全キーが RAM に収まる → アペンドオンリー + ハッシュ索引が最適
- 更新・削除がある → アペンドオンリーは GC / Compaction を必要とし、LSM に対する単純さの利点が消える
- 範囲検索・`ORDER BY`・2 次索引がある → B+木
- 必要なのが耐久性だけ → **WAL としてアペンドオンリーを使う**（主ストレージにはしない）

## Rationale

- RDBMS の主ストレージには範囲検索・順序・更新・2 次索引が必要で、単純な追記ログだけでは不足する
- 追記専用の利点は、WAL と監査 / イベントログという**適切な境界**で活かせる
- ADR 0001 の WAL はすでにアペンドオンリーであり、判断の一部は既存設計に取り込み済みである
- 初期プロトタイプの最小永続化としては有用だが、そのまま最終形にはできない

## Consequences

### 良い面

- WAL・監査ログ・イベントログでは高い追記性能と単純さを得られる
- 障害復旧の仕組みを小さく理解できる
- 初期プロトタイプを早く動かせる

### 悪い面 / 注意点

- 主ストレージにすると範囲検索と SQL 機能が大きく制限される
- 更新・削除を扱うには結局 GC / Compaction が必要になる
- 起動時リカバリのために checkpoint / snapshot が必要
- インメモリハッシュ索引方式はキー数が増えると破綻する

## Open Questions

- WAL のレコードフォーマットと checkpoint 方式（ADR 0001 から継続）
- 監査ログ / イベントログを独立コンポーネントとして持つか
- 初期プロトタイプでアペンドオンリーをどこまで使い、いつ B+木セグメントへ移行するか

## Revisit Conditions

以下に該当したら本 ADR を見直す。

- 対象ワークロードが追記専用（イベント / ログ / 時系列）に絞られた
- 全キーが RAM に収まる組み込み用途に限定すると判断した
- B+木セグメントの実装が重く、まず永続化だけの最小構成が必要になった
- 範囲検索が不要になり、点検索と追記だけで足りるようになった
