# ADR 0005: memtable のバッファリング運用と書き込み経路の耐久性を決定する

- Status: Accepted
- Date: 2026-11-17
- Related: [ADR 0001](0001-storage-engine-b-plus-tree.md) / [ADR 0004](0004-compaction-strategy.md) / [設計・実装チェックリスト](../design-checklist.md) 1.1.1 / 3.1

## Context

ADR 0001 で「WAL → memtable → immutable memtable → Compaction → 不変 B+木セグメント」という書き込み経路を採用し、ADR 0004 で memtable 64 MiB・L0 トリガ 4 本などのパラメータを決めた。しかし**運用の規則**は未決だった。

- memtable の容量を何で計測し、いつローテーションするか
- immutable memtable を何本保持し、詰まったときに書き込みをどうするか
- flush を誰が実行し、WAL とどう対応させるか
- メモリをどう確保し、いつ解放するか
- 未コミットのデータをいつ memtable に載せるか
- クライアントに成功を返す条件と fsync のタイミング

チェックリスト 1.1.1 の「メモリ層でのバッファリング / 遅延書き込み」は、この運用規則が決まって初めてチェックできる。本 ADR はその決定を記録する。

なお本 ADR が扱うのは**いつ** ack するか / **いつ** fsync するか / **いつ** WAL を捨てるかまでとする。WAL のレコードフォーマット・リカバリ手順・checkpoint の詳細は 3.1 で決める。

## Decision

### 1. 容量は arena の確保バイトで計測する

memtable のサイズは、キー・値の論理バイトではなく **arena が確保した実バイト数**で計測する。

- スキップリストのノード（多段ポインタを含む）も arena から確保するため、実メモリ使用量と一致する
- ローテーション判定は「arena の確保バイト >= 64 MiB」で行う
- 論理バイトとの乖離（オーバーヘッド係数）を推測しなくてよい
- 計測誤差を許容しない代わりに、実装は arena アロケータの使用量カウンタを参照するだけなので単純

### 2. ローテーションはサイズ + アイドル時間で行う

- **基本**: arena の確保バイトが 64 MiB に達したらローテーション
- **追加**: 最後の書き込みから **30 分以上**アイドルが続いたら、データが空でない場合に限り強制 flush
- アイドル判定は flush スレッドが定期的（1 秒間隔程度）に最終書き込み時刻と現在時刻を比較する
- 強制 flush も通常のローテーションと同じ経路を通す（immutable 化 → flush → WAL 切り替え）

アイドル flush の目的は、書き込みが止まった状態でメモリと WAL を解放し、次回起動時のリカバリ時間を短くすることにある。

### 3. immutable memtable は 1 本だけ保持する

- 現行 memtable + immutable memtable の 2 本体制とする
- 読み取り経路は `現行 memtable → immutable → L0 → L1 → …` で固定され、探索対象が増えない
- flush の順序も FIFO で自明になる

### 4. immutable が詰まったら書き込みをブロックする

- immutable の flush が完了する前に現行 memtable も満杯になった場合、書き込みスレッドをブロックする
- タイムアウト・エラーは初期実装では入れない（挙動を単純に保つ）
- ブロックは flush スレッドの完了で解除されるため、無限待ちにはならない
- L0 の stall（8 / 12 本、ADR 0004）と合わせて二段構えのバックプレッシャになる

### 5. flush は専用スレッド 1 本が実行する

- flush 専用スレッドを 1 本立て、immutable を FIFO で処理する
- 書き込みスレッドは flush を行わない（レイテンシの予測可能性を優先）
- flush の処理内容は「スキップリストをキー順に走査 → B+木セグメントを bulk load → manifest に追記 → arena 解放」

### 6. WAL は memtable のローテーションに連動して切り替える

- memtable を immutable にした時点で、新しい memtable と**新しい WAL ファイル**を用意する
- 書き込みは常に「現行 memtable に対応する WAL」へ追記する
- これにより、WAL の再生範囲と memtable の対応が 1 対 1 になり、リカバリが単純になる

### 7. 古い WAL は manifest への追記後に削除する

削除条件は「その WAL に対応する memtable の flush が完了し、結果が manifest に追記されていること」。

順序は以下に固定する。

1. セグメントを一時ファイルへ書き、fsync
2. rename で確定
3. manifest に VersionEdit を追記し、fsync
4. メモリ上の version を差し替え
5. 対応する WAL を削除
6. immutable の arena を解放

manifest 追記より前に WAL を消すと、クラッシュ時に「セグメントにも manifest にも無く、WAL にも無い」データが生じる。この順序はクラッシュ安全の前提なので変更しない。

### 8. メモリ総量の上限を決め、memtable は 2 本分を確保する

- プロセス全体のメモリ上限を設定値として持つ
- そのうち memtable（現行 + immutable）の 2 本分を常に確保できることを不変条件とする
- 残りは将来のブロックキャッシュ・Compaction のバッファに配分する
- 2 本分は「予算」であり、起動時に 128 MiB を物理確保するわけではない。arena は必要に応じて伸ばす
- 総量の初期値は実測前の暫定値とし、本 ADR では**不変条件のみ**を決定する

### 9. memtable のメモリは arena から確保する

- memtable ごとに arena アロケータを持ち、スキップリストのノードとキー・値をすべてそこから確保する
- スキップリストは順序構造のみを持ち、実体は arena に追記されていく（追記型バッファと順序構造の両立）
- flush 完了後に arena を丸ごと解放する。個別ノードの解放は行わない
- Zig に GC がないため、ノード単位の回収を持ち込まないことが安全性につながる

### 10. 未コミットデータはコミット時に一括適用する

- トランザクション中の変更は memtable に載せず、コミット時にまとめて適用する
- したがって memtable には**コミット済みのデータしか存在しない**
- 可視性判定は `seq <= snapshot` だけで完結し、未コミットを隠すための追加構造を持たない
- ロールバックは「適用前に破棄する」だけで済み、undo レコードを必要としない
- 制約: トランザクション中に自分の書き込みを読む（read-your-writes）には、別途バッファを持つ必要がある

### 11. ack は WAL が OS バッファに到達した時点で返す

書き込みの順序を以下のように固定する。

1. WAL へレコードを `write()` する（OS バッファへ）
2. `write()` が成功したことを確認する
3. memtable へ適用する
4. クライアントへ成功を返す

**不変条件: memtable に存在するデータは、必ず WAL にも書かれている。** この順序を守ることで、プロセスクラッシュ時は WAL の再生で復旧できる。

fsync は ack の後にまとめて行うため、ack のレイテンシに fsync は含まれない。

### 12. group commit は件数上限と極短タイムアウトの組み合わせで発火する

- 未 fsync のレコードが **64 件**に達するか、**100 µs** 経過するかの早い方で fsync を実行する
- 値は初期値であり、実測で調整する
- タイムアウトだけにすると 1 件ずつ fsync に近づき、件数だけにすると低負荷時に fsync が遅延するため、両方を併用する

### 13. fsync ポリシーは「group commit ごと」を既定とし、定期モードを設定で選べる

- **既定**: group commit のバッチごとに fsync
- **設定**: 定期モード（例: 1 秒間隔）を選べる。スループット優先のバルクロード向け
- **設定**: `sync_commit` を有効にすると、fsync 完了後に ack を返す（耐久性優先）。既定では無効

### 14. rename・新規ファイル作成時はディレクトリも fsync する

- セグメントの rename、WAL の新規作成、manifest の追記後は、対象ディレクトリを fsync する
- ファイルだけを fsync しても、ディレクトリエントリの変更が永続化される保証はないため

## 耐久性の保証範囲

ack を OS バッファ到達時点で返すため、保証は以下のようになる。**この表を運用上の前提とする。**

| 障害 | 失われるデータ | 復旧方法 |
|---|---|---|
| プロセスクラッシュ | なし（WAL は OS バッファに残る） | WAL 再生 |
| OS クラッシュ | 直近 1 group commit バッチ分（最大 64 件 / 100 µs 相当） | WAL 再生（末尾の不完全レコードは破棄） |
| 電源断 | 同上。加えて OS バッファの未書き戻し分 | WAL 再生 |
| `sync_commit` 有効時 | なし（fsync 完了後に ack） | WAL 再生 |

## 構成

```
書き込みスレッド
   │ 1. WAL write()      → OS バッファ
   │ 2. memtable 適用（arena + skiplist）
   │ 3. ack
   ▼
[現在 memtable] ──64MiB / 30分アイドル──▶ [immutable]（1 本のみ）
   │                                          │ flush スレッド（1 本）
   │                                          ▼
   │                              B+木セグメント構築（bulk load）
   │                                          │ rename + fsync
   │                                          │ manifest 追記 + fsync
   │                                          ▼
   │                              WAL 削除 → arena 解放
   │
   └─ 新 memtable + 新 WAL

group commit スレッド: 64 件 or 100 µs で fsync
```

## Rationale

- **arena 実測**にすることで、memtable のメモリ上限が実使用量と一致し、2 本分の予算管理が正確になる
- **immutable 1 本 + ブロック**は、読み取り経路と flush 順序を固定できる最も単純な構成。バックプレッシャは L0 の stall と組み合わせて二段構えになる
- **コミット時一括適用**により、memtable の内容と可視性判定が一致し、未コミット除外のための追加データ構造が不要になる
- **WAL を memtable と 1 対 1 で対応**させると、リカバリ時に「どの WAL をどこまで再生するか」が自明になる
- **ack を OS バッファ到達時**にすることで、fsync のレイテンシを書き込みパスから外せる。失われうる範囲は group commit の窓で上限が決まる
- **アイドル flush** は、書き込みが止まったときにメモリと WAL を解放し、次回起動のリカバリ時間を短くする

## Consequences

### 良い面

- memtable のメモリ使用量が実測で把握でき、上限管理が正確になる
- 読み取り経路が `memtable → immutable → L0 → …` で固定され、探索対象が増えない
- 未コミットデータの除外が seq だけで済み、MVCC 導入時の変更範囲が小さい
- ack が fsync に依存しないため、書き込みスループットとレイテンシが安定する
- WAL と memtable が 1 対 1 なので、クラッシュリカバリの実装と検証が単純になる
- arena の一括解放により、Zig でノード単位の回収を設計しなくてよい

### 悪い面 / 注意点

- **電源断・OS クラッシュで最大 1 group commit バッチ分のコミットが失われる**。ACID の D を厳密に要求する用途では `sync_commit` を有効にする必要がある
- immutable 1 本のため、flush が遅いと書き込みがブロックする。L0 の stall と合わせてスループットの上限が決まる
- アイドル flush は小さいセグメントを生成しやすい（1 件だけ書いて 30 分放置すると 1 件のセグメントができる）。L0 tiered が 4 本でまとめてマージする前提で吸収するが、書き込みとアイドルを繰り返すワークロードでは write amp が上がる
- arena 実測は論理サイズより大きく、同じ 64 MiB でも保持できるエントリ数はキー長・値長に依存する
- コミット時一括適用のため、トランザクション中の read-your-writes には別途バッファが必要
- macOS では `fsync()` が物理書き込みを保証しない。`F_FULLFSYNC` の要否を別途決める必要がある

## Open Questions

- プロセス全体のメモリ上限の初期値と、memtable 以外（ブロックキャッシュ・Compaction バッファ）への配分
- アイドル 30 分の妥当性と、小セグメント発生を抑える最小サイズ閾値の要否
- ブロック時のタイムアウト・エラー導入の是非（計測後）
- group commit の 64 件 / 100 µs の実測調整
- macOS の `F_FULLFSYNC` を既定で使うか
- `sync_commit` を有効にした場合のスループット影響
- トランザクション中の read-your-writes をどう保持するか（トランザクションバッファの設計）
- WAL レコードのフォーマットとリカバリ手順（3.1 で決定）

## Revisit Conditions

以下に該当したら本 ADR を見直す。

- flush の追従遅れによる書き込みブロックが常態化した（→ immutable を複数本にする / flush を並列化する）
- 電源断でのデータ損失が許容できない要件になった（→ `sync_commit` を既定にする）
- アイドル flush による小セグメントで write amp が悪化した（→ 最小サイズ閾値の導入 / アイドル時間の延長）
- メモリ上限に達して OOM が発生した（→ 配分とバックプレッシャの再設計）
- group commit の窓が p99 レイテンシや ARIES 的な耐久性要件と合わなくなった
