# RDBMS 自作 設計・実装チェックリスト

## 1. ストレージエンジン (Storage Engine)

データをディスクやメモリにどのように配置し、管理するか。

### 1.1 データ構造の選択

- [ ] B+木（MySQL / PostgreSQL などで一般的）を採用するか判断
- [ ] LSM ツリー（書込最適化）を採用するか判断
- [ ] 単純なアペンドオンリー（ログ型）を採用するか判断
- [ ] 対象ワークロード（読み込み重視 / 書き込み重視）を整理

### 1.2 ファイルフォーマット

- [ ] データを固定長で区切る「ページ（Page / Block）」のサイズを決定
- [ ] ページヘッダの設計（ページID、種別、空き領域、チェックサムなど）
- [ ] ページ内の「スロット（Slot）」構造を設計
- [ ] レコード（タプル）のレイアウトを設計（NULL ビットマップ、固定長 / 可変長部）
- [ ] 空き領域管理（フリースペースマップなど）を実装
- [ ] ファイルとページの対応（ヒープファイル、セグメント、テーブルスペース）

### 1.3 バッファプールマネージャー

- [ ] メモリ上にページをキャッシュする仕組みを実装
- [ ] ページ置換アルゴリズムを選択（LRU / Clock / LRU-K など）
- [ ] ピン留め（pin / unpin）とダーティページ管理
- [ ] ページ書き戻し（flush）とチェックポイントの連携
- [ ] 同時アクセス時のラッチ / ロック設計

### 1.4 可変長データの扱い

- [ ] VARCHAR / BLOB など可変長型の格納方法を決定
- [ ] 1ページに収まらない巨大データの退避機構（オーバーフローページ / TOAST 相当）
- [ ] 圧縮・外部ファイル格納の要否を検討

## 2. クエリプロセッサ (Query Processor)

SQL 文字列を受け取って実行するまでの一連の流れ。

### 2.1 パーサー (Parser)

- [ ] 字句解析器（Lexer / Tokenizer）を実装
- [ ] 構文解析器を実装（再帰下降パーサー、または Lex / Yacc 系の生成器）
- [ ] 抽象構文木（AST）のデータ構造を設計
- [ ] 構文エラー時のメッセージと位置情報を設計
- [ ] 対応する SQL サブセットを定義（SELECT / INSERT / UPDATE / DELETE / DDL / JOIN / 集約など）

### 2.2 カタログ / メタデータ管理

- [ ] テーブル定義・カラム型の管理方法を設計
- [ ] インデックス情報の管理
- [ ] 制約（PRIMARY KEY / UNIQUE / NOT NULL / FOREIGN KEY / CHECK）の管理
- [ ] 権限・ロール情報の管理
- [ ] システムスキーマ（システムカタログ）の持ち方を決定

### 2.3 オプティマイザ (Optimizer)

- [ ] 論理プランへの変換（バインディング・名前解決・型解決）
- [ ] 初期実装としてルールベース最適化（RBO）を用意
- [ ] 統計情報の収集（行数、カーディナリティ、ヒストグラムなど）
- [ ] コストベース最適化（CBO）への発展
- [ ] アクセスパス選択（フルスキャン / インデックススキャン / インデックスオンリースキャン）
- [ ] JOIN 順序・結合アルゴリズムの選択（Nested Loop / Hash Join / Merge Join）
- [ ] 実行計画（Execution Plan）の表現と `EXPLAIN` 出力

### 2.4 エグゼキュータ (Executor)

- [ ] Volcano モデル（Iterator モデル：`open()` / `next()` / `close()`）の採用を検討
- [ ] 実行計画ツリーの構築と実行
- [ ] 各オペレータの実装（Scan / Filter / Project / Join / Aggregate / Sort / Limit）
- [ ] 式評価エンジン（比較・算術・関数呼び出し）
- [ ] 型変換と NULL の三値論理の扱い
- [ ] ソート・集約の外部メモリ退避（スピル）

## 3. トランザクションと並行性制御 (ACID 特性)

複数のクエリが同時に動いてもデータの整合性を保つ最重要コンポーネント。

### 3.1 WAL (Write-Ahead Logging)

- [ ] データを直接書き換える前に変更履歴をディスクへ同期する仕組みを実装
- [ ] ログレコードのフォーマット（LSN、トランザクションID、REDO / UNDO 情報）を設計
- [ ] ログバッファと fsync のタイミングを決定
- [ ] チェックポイント処理
- [ ] クラッシュリカバリ（REDO / UNDO フェーズ）

### 3.2 並行性制御 (Concurrency Control)

- [ ] 2相ロック（2PL）による整合性確保を検討
- [ ] MVCC（多版同時実行制御）の採用を検討（読込と書込をブロックしない）
- [ ] バージョン管理方法（UNDO ログ / タプル内バージョンチェーン / 追記型）
- [ ] ロック粒度（行 / ページ / テーブル）の決定
- [ ] ロックモード（共有 / 排他 / インテンションロック）の設計
- [ ] 不要バージョンの回収（VACUUM / GC）

### 3.3 分離レベル (Isolation Levels)

- [ ] Read Uncommitted の実装方針
- [ ] Read Committed の実装方針
- [ ] Repeatable Read の実装方針
- [ ] Serializable の実装方針（SSI など）
- [ ] 分離レベルごとの異なる読み取り現象（ダーティリード / ファントムリードなど）の扱いを整理

### 3.4 デッドロック検知

- [ ] 待ち行列（Wait-for Graph）の管理
- [ ] 循環待ちの検知
- [ ] 犠牲トランザクションの選定と強制アボート
- [ ] ロックタイムアウトの実装

## 4. ネットワークとプロトコル

クライアント（アプリケーション）と DB サーバーが通信する方法。

### 4.1 接続モデル

- [ ] プロセス駆動型（PostgreSQL 方式：接続ごとにプロセスをフォーク）を検討
- [ ] スレッド駆動型（MySQL 方式：スレッドプール等で管理）を検討
- [ ] シングルプロセス / 組み込み型（SQLite 方式：ライブラリとしてインプロセス動作、ネットワークなし）を検討
- [ ] 接続プーリングと同時接続数の上限設計

### 4.2 通信プロトコル

- [ ] テキストベースか独自バイナリプロトコルかを決定
- [ ] ハンドシェイク / 認証フローの設計
- [ ] メッセージフレーミングとバージョニング
- [ ] クエリ送信・結果セット返却・エラー通知のフォーマット
- [ ] 既存プロトコル（PostgreSQL Frontend/Backend プロトコルなど）への互換性の要否を判断

## 参考：有名 RDBMS の特性比較

自作するデータベースの「方向性」を決めるための比較表。

| 項目 | MySQL (InnoDB) | PostgreSQL | SQLite |
| --- | --- | --- | --- |
| アーキテクチャ | クライアント・サーバー型 | クライアント・サーバー型 | インプロセス（組み込み型） |
| 並行処理モデル | マルチスレッド | マルチプロセス | シングルプロセス（ファイルロック） |
| 主なデータ構造 | B+木（インデックス構成テーブル） | Heap ファイル + B+木インデックス | B 木 / B+木 |
| 型システム | 厳格（設定による） | 非常に厳格（拡張可能） | 動的（型アフィニティ） |
| ソースコード規模 | 巨大・複雑 | 巨大・整然 | コンパクト（1ファイルに凝縮可能） |
